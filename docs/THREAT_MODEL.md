# R.O.F.I.E.S Repository Threat Model

## Overview

This repository implements an institution-facing equipment borrowing system. Next.js renders applicant, member, and staff experiences and exposes bounded route handlers; Supabase Auth establishes an email/password session; PostgreSQL is authoritative for applications, permissions, reservations, custody, inventory, audit history, and in-app notifications; private Supabase Storage holds processed equipment photographs and, in a separate bucket, short-lived college-ID images. Production code is under `src/` and `supabase/migrations/`. Tests, fictional seed data, screenshots, and local recovery scripts are developer-controlled evidence rather than runtime authority.

The primary assets are authentication credentials and recovery channels, institutional identity and contact data, college-ID images and review decisions, borrower history, current custody, stock and condition, precise storage details, staff capabilities, append-only audit history, exports, provider credentials, and recoverability. The most important security outcomes are preventing credential abuse, unauthorized ID-document access, cross-borrower disclosure, forged privilege, self-approval, over-allocation, negative stock, false-success responses, secret exposure, and destructive history correction.

## Threat Model, Trust Boundaries, and Assumptions

Trust boundaries are:

1. The untrusted browser to the Next.js server. Search text, route parameters, JSON, form data, filenames, captions, origins, cookies, and idempotency keys are attacker-controlled. React escaping, Zod schemas, exact-origin checks, size bounds, generated object names, rate limits, and generic errors constrain this boundary.
2. Next.js to Supabase Auth/Data API/Storage. The browser receives only the publishable key. Cookie-backed user clients retain the caller identity; server-only privileged clients are narrowly limited to vetted image writes/deletes and administrative commands. The applicant never receives a durable college-ID object URL.
3. The Data API to PostgreSQL. Explicit grants, RLS, active-account and approved-member policies, fixed-search-path security-definer functions, transaction locks, constraints, and atomic audit/notification writes are the decisive controls.
4. Authorized reviewers to private college-ID objects. Review access requires a server-side capability check, a short-lived object response or signed URL, no shared caching, and an immutable document-access audit event. A retention job deletes the object 30 days after approval or rejection while preserving non-image decision metadata.
5. Supabase Auth to institution-owned SMTP. This boundary carries confirmation, password-reset, and security mail only. It must never be used for borrowing, return, reminder, or other application events.
6. Operators and deployment systems to secrets, migrations, backups, retention jobs, and role administration. These inputs are operator-controlled and require environment isolation, recent authentication, reviewed migrations, protected CI settings, and institution incident procedures.
7. Developers to dependencies, source, seed data, and CI. Lockfile reproduction, dependency audit, secret scanning, review, and migration tests reduce supply-chain and accidental-secret risks.

Assumptions: Supabase and Vercel correctly provide TLS, secure session cookies, password hashing, token verification, and managed isolation; the institution controls the accepted email domain and SMTP configuration; administrators protect their accounts and environment settings; production uses `ROFIES_DEMO_MODE=false`; and deployment config does not expose service-role, retention-job, or SMTP secrets. Compromise of a cloud control plane or an administrator with database-owner access is outside application-level prevention, but audit, backup, key rotation, retention verification, and incident response remain in scope.

## Attack Surface, Mitigations, and Attacker Stories

- Authentication/session abuse: an attacker guesses passwords, enumerates accounts, registers a look-alike domain, reuses a recovery token, or continues with a deactivated account. Supabase Auth protections, strong-password and leaked-password controls, generic responses, rate limits, server-side confirmed-domain checks, session refresh, active-profile RLS guards, and capability functions constrain these attacks. A confirmed account remains an applicant and receives no catalog or borrowing access until an authorized admin approves it.
- Applicant/ID abuse: an applicant uploads malicious bytes, replaces evidence after review, reads another applicant's ID, or forces indefinite retention. Server processing validates type and size, strips metadata, generates object paths, denies direct listing/public access, binds one current document to the application, audits every reviewer read, prevents applicant reads after submission, and makes deletion due 30 days after a final decision observable and retryable.
- Object-level authorization: a member changes an identifier to read another borrower or a staff-only record. RLS ownership policies, page capability guards, security-definer predicates, non-disclosing 404 responses, and the authorization matrix protect the primary and direct-API paths.
- Business-logic races: two staff users approve the last unit, hand over one reservation twice, or race a return against another resolution. Command functions use row/advisory locks, transaction-time availability, state predicates, constraints, and idempotency records; losing races return deterministic conflicts.
- Injection and unsafe output: remarks, search, CSV cells, captions, or errors carry SQL, HTML, formula, or log payloads. SQL is parameterized, structured inputs are bounded, React escapes text, no unsafe HTML sink exists, CSV cells are neutralized, and telemetry is allowlisted/redacted.
- CSRF/XSS/clickjacking: a hostile site submits cookie-authenticated commands or injects script. Mutations require an exact configured Origin; pages use per-request nonce CSP, strict-dynamic scripts, frame-ancestors none, MIME/referrer/permissions policies, and no third-party runtime script.
- Upload abuse: a staff user or applicant submits a polyglot, huge, animated, metadata-bearing, or path-controlled file. The server decodes only supported formats, bounds pixels/dimensions/bytes, rejects multiple frames, strips metadata, re-encodes to a safe format, and generates the object name. Direct public writes are denied; equipment-photo registration is capability-scoped; college-ID writes are bound to the caller's editable application; failed database registration removes the object.
- Export/privacy abuse: an unauthorized user requests CSV or spreadsheet content becomes executable. The route rechecks `reports:export`, uses a narrow database function, bounds rows, prevents caching/sniffing, and neutralizes formulas.
- Service credential misuse: a browser bundle, object URL, error, or log exposes a service/SMTP secret or private ID. Server-only environment validation, narrow adapters, redaction, secret scanning, non-public buckets, and access-audit review protect these assets.
- Exceptional conditions: database, authentication email, storage, cleanup-job, or network failures create a false success, duplicate event, orphaned image, or retention breach. Business commands respond only after commit; business state and its in-app notification commit together; retries use deduplication keys; failed upload registration removes the object; deletion retries remain visible until reconciled; maintenance mode fails writes closed; reconciliation preserves actual and recorded times separately.
- Supply-chain/deployment compromise: a malicious package, action, or preview configuration reaches production. The pinned lockfile, minimal runtime dependencies, read-only CI permissions, dependency audit, separate-environment policy, and required pre-deployment review reduce likelihood. Deployment remains a user-authorized external action.

SSRF is low relevance because user input cannot select an outbound URL and application notifications make no outbound provider call. Password guessing, account enumeration, recovery abuse, and signup flooding are directly relevant under email/password authentication and require Supabase Auth controls plus application-level rate limits and generic responses. Multi-tenant isolation between institutions is out of scope because the first release has one configured institutional domain, but applicant, document, and borrower-level isolation remain mandatory.

## Severity Calibration (Critical, High, Medium, Low)

- Critical: remote unauthenticated service-role disclosure; arbitrary database-owner execution; a mutation path that can silently create unlimited stock/custody corruption across the system; destructive loss of audit and backup recovery.
- High: authenticated cross-borrower history disclosure at scale; staff-capability forgery; self-approval or concurrency bypass that overbooks/duplicates handovers; upload-driven server code execution; production demo mode accepting fake commits.
- Medium: a bounded CSRF mutation, stored script in staff-visible content, unauthorized limited CSV, unbounded retry causing operational denial, or exposure of precise locations/internal remarks to ordinary members.
- Low: isolated non-sensitive catalog metadata leakage, missing defense-in-depth header without an injection primitive, minor rate-limit bypass with no state/integrity impact, or verbose operational timing without identity or secret content.

Severity can fall when exploitation requires a protected operator account and affects only reversible configuration, and rises when a flaw crosses borrower privacy, inventory authority, or immutable audit boundaries. Scanner output is treated as a lead and requires code-path and role validation.
